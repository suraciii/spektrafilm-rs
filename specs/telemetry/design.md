# Telemetry design

## Boundary

An operation owns its report from acceptance of an executable request through its terminal outcome. File chooser interaction and parameter editing are outside the operation. GUI debounce delay before acceptance is outside operation duration. The operation carries the input and parameter revisions captured by its worker. Save refers to the retained output's render identity and owns only its saving work.

The frontend owns request acceptance, input loading, worker handoff, presentation handoff, and file publication. Runtime owns preparation and simulation observations. The compute backend owns actual dispatch, submission, transfer, cache, and GPU timing observations. The native writer owns encoding and metadata observations. Lower layers must not infer frontend intent from environment variables or backend names.

Observations must attach to the current operation explicitly. A backend may serve multiple operations; it must not maintain an unqualified mutable "last render" report. Existing last-call timing accessors retain their public behavior, but they must not supply operation attribution under concurrency. Worker results must carry their report to the owner that accepts, rejects, or publishes the result.

A caller must propagate the operation context across spawned threads and bounded tasks that emit observations. Pure per-pixel Rayon work needs no telemetry context or span entry. CPU stage timing must enclose the stage call once, rather than create events per pixel. A `tracing` span must be entered on the thread that emits its work observations. Backend work must carry its parent operation and stage so GPU work cannot be attributed to a concurrent request.

The shared typed observation vocabulary must live below core in the existing GPU crate so model and backend code do not acquire a dependency on core. Core owns the complete operation report and its serialization; frontends own collection selection and report storage. A scoped backend view may bind an operation sink to the existing `ComputeBackend` interface, but it must share the original device and cache. Default backend implementations must identify the CPU work they actually perform. Instrumentation must not require a second rendering pipeline or a new telemetry crate. Context must be passed explicitly through the operation's borrowed sink or scoped backend view; a thread-local current report is not an attribution boundary.

## Collection and signals

The system must use one operation-local observation source for local reports and `tracing` events. Stable event names and typed numeric fields must represent starts, routing decisions, backend batches, and terminal outcomes. Timing values must not be formatted strings. Span hierarchy must describe operation, phase, stage, and backend batch ownership.

Summary mode collects fixed-size counters, bounded phase observations, and routing facts. GPU timing mode adds timestamp queries to existing compute passes. Neither mode may add image readbacks, image copies, retries, simulation passes, or synchronization points for observation. Query results may use a small auxiliary readback alongside an existing completion boundary. Collection must not create per-pixel observations.

Each operation must retain at most 1,024 detailed observations across attempts, phases, stages, batches, and passes. It must retain root outcome, configuration, exact total work counters, and fixed-category duration totals outside this detail limit. Later observations must update those totals and mark detail as truncated without allocating more detail. A child that cannot retain its parent must also be omitted. Retained diagnostic data must occupy at most 1 MiB per operation, excluding temporary JSON serialization; exhausting this byte limit must stop detail retention and report truncation. The report must identify its limits, retained and omitted observation counts, and covered timing scope. Counter overflow must report an unavailable value rather than wrap. The observation source must not allocate image-sized storage.

Disabled collection must not add telemetry records, formatted fields, query resources, or synchronization beyond existing public timing behavior. Existing Runtime timing maps are a separate compatibility cost; removing them requires a separate API decision. Stage-level collection must not introduce a process-wide contended lock. Local structured telemetry events must use the report's field allowlist and privacy rules. Existing human application logs remain outside the shareable report.

The local report is the diagnostic source of truth for a completed operation. `tracing` is the causal event surface and can support external CPU profilers. The target system does not require an OpenTelemetry SDK, collector, metrics server, or exporter. This choice keeps local operation attribution independent of process-wide aggregation and avoids a second exporter lifecycle. Metric names, units, and bounded dimensions remain suitable for a separately authorized OpenTelemetry integration.

Event filtering must not change explicitly requested report collection. Summary collection must cover every accepted operation while enabled. Pass timing must apply to the selected operations consistently; a report must identify its requested and effective collection mode. Unsupported GPU timing retains summary with a stable availability reason. A benchmark that selects only some iterations for timing must report that selection. Aggregates must identify sample count and must not silently combine collection modes.

## Routing and timing

Runtime reports the resident eligibility decision separately from the route that actually executed. A declined resident route can still dispatch GPU stages. The backend reports actual executed work; it must not count work from requested or prepared parameters. CPU implementations used inside a WGPU backend must report CPU execution.

Host durations use a monotonic clock. Each observation must name its boundary and parent. Phase and stage durations are inclusive wall durations; backend batch durations nest within stages. Nested durations must not be summed as if they were disjoint. Cross-thread overlaps must remain visible rather than be converted into a serial total.

A backend batch covers host preparation, command submission, completion wait, and result materialization. Host preparation can include parameter conversion, cache lookup, resource creation, upload calls, and command encoding. It is not CPU utilization. Submit-to-map-ready includes submission overhead, queue contention, device work, staging copies, driver scheduling, callback scheduling, and host wakeup. It is not kernel time. Materialization covers mapped-range access, CPU copying, scalar conversion, result construction, and unmap work.

At compute-device creation, the backend must request adapter-supported `TIMESTAMP_QUERY` as an optional capability regardless of current collection mode. It must allocate query resources and write timestamps only for operations captured in GPU timing mode. This allows session mode changes without recreating the active device. Each Adapter object must receive at most one device request. If optional-feature device creation fails, initialization must request one fresh Adapter with the same selection options and make one baseline device request using the existing feature and limit policy. A fresh adapter request does not guarantee the same physical device; the report must identify the final adapter actually used. This initialization policy must be identical in all collection modes and must not broaden adapter selection or required timestamp features. Failed baseline initialization retains the existing backend-unavailable behavior. Timing must remain unavailable as `feature_request_failed` after a successful baseline request. Summary mode and off mode must use unchanged image commands.

The backend must convert timestamp differences with that queue's timestamp period. Pass records must identify their batch and pass occurrence. Query resolution and telemetry buffer copies are observation overhead and must be separate from application work counts. Invalid, unresolved, or unsupported queries must produce unavailable observations with reasons. Timing must not request broader inside-pass or inside-encoder timestamp features when pass boundaries suffice.

Each timed compute pass uses two query slots. One batch must use at most 2,048 query slots, including only pass records admitted by the detail limit. It must resolve the used contiguous range at offset zero into a `QUERY_RESOLVE | COPY_SRC` buffer, then copy its 8-byte results to a separate `COPY_DST | MAP_READ` buffer. Query resources must be owned by the batch until mapping ends. They must not be reused across in-flight batches. Query counts, feature availability, resolve offset, and buffer sizes must be checked before encoding image commands. Unavailable capability or exhausted detail budget must disable timestamps for that batch. Resource allocation or encoding errors that invalidate device work are real backend failures, not reasons to repeat image execution.

Image and query map callbacks must be registered before the existing completion poll. The result must not add a blocking wait or a second submission solely to obtain query results. Query results still pending at image completion must be unavailable as `not_ready`; batch-owned cleanup must release them safely without delaying publication. A query map failure after valid image completion must be unavailable as `query_failed`. Both cases must preserve valid image results. Actual command failure and device loss retain normal execution failure handling.

A pass duration covers the device's pass interval. It does not measure isolated shader instructions, CPU work, queue delay before the pass, or physical transfer bandwidth. A sum of pass durations must be named `compute_pass_sum`; it must not be described as operation GPU duration or subtracted from host time to estimate CPU time.

## GPU accounting

Logical upload and readback account for bytes crossing the application host/device boundary. They do not claim physical PCIe traffic. A shared-memory or directly mapped path still has logical transfers. Device-to-device staging copies have separate counters and must not be added to logical readback bytes a second time.

Work counts must include actual backend calls for both full-image simulation and calibration work within the operation. Purpose distinguishes `image`, `calibration`, and `telemetry`. A report must not hide calibration uploads behind a one-upload resident description. GUI texture presentation belongs to the presentation phase and must not enter the simulation backend's GPU work counts.

Shared-queue submission order and global error scopes can include other operations. Work counters must attribute writes and commands to the operation that issued them, regardless of which submission flushes a scheduled write. Observations must identify shared device use. Completion waits include interference from other queued work; they must not be presented as isolated operation service time. Telemetry must not introduce a device-wide serialization lock. It must not push recovery error scopes on a device already shared with concurrent work. Error-scope capability validation may occur only before the device is exposed to workers; batch map callbacks supply recoverable query-readback errors. Normal uncaptured allocation, validation, and device errors must retain execution failure semantics.

Requested GPU buffer bytes describe API resource sizes. They do not describe committed VRAM, allocator residency, or driver pools. A resource is owned by the operation, shared cache, or presentation subsystem. Shared cache resources must not be charged as new operation allocations on a hit. Physical device memory and process memory require separate measured sources.

## Terminal records and overhead

The frontend finalizes the record at the [operation terminal boundary](metrics.md#operation-and-phase-wall-time). CPU or GPU failure may leave partial observations; those values must identify their completed scope. Telemetry persistence errors must not rewrite the operation outcome. Preview completion ends at the presentation handoff, not at physical display scanout.

Detailed reports must use stable schema fields and stable enumerated categories. Paths and raw exceptions must not enter those fields. Operation and revision identifiers are correlation fields for local reports and traces; they must not become metric labels. Device names, stock identifiers, dimensions, seeds, and arbitrary user strings must not become aggregate metric labels.

Validation must compare telemetry-off and telemetry-on image results using existing numerical budgets. A controlled warm/cold comparison must measure collection overhead on each exercised route and identify the adapter, dimensions, precision, and iterations. The implementation must report measured overhead rather than assume a universal percentage. CPU and driver profilers remain external tools for instruction-level attribution.

Summary overhead acceptance must use paired telemetry-off and summary runs with identical reuse conditions on CPU, resident, and per-stage routes. After one setup run, it must collect at least ten alternating measured pairs per route and retain individual times. The median increase must not exceed the greater of 5 milliseconds or 3 percent of the off-mode median; a breach blocks overhead acceptance for that route. GPU timing overhead must be measured and shown separately, because pass queries can perturb device scheduling. Software-adapter evidence must not be used to claim hardware-driver overhead acceptance.
