# Export contract implementation note

This note records the GUI render, Save and Export contracts and the verification limits below.

## Present in this worktree

- **Preview and Scan:** Preview uses the configured reduced long-edge limit and preview digestion. Scan uses the full input and retains full-resolution output, preferring GPU execution with CPU fallback and faithful CPU stages for unsupported effects. The viewport samples that retained image for visible detail at fit, 100%, 200% and 400%; the preview limit does not cap Scan's available detail.
- **Save:** Save writes the latest retained floating output without rendering again. The suggested filename ends in `.jpg`; the chosen extension selects JPEG8, PNG8, TIFF16 integer with ZIP compression, or OpenEXR16 half. Conversion uses the current simulation saving color space and transfer encoding, with no forced ACES or linear encoding. Save leaves JPEG quality and subsampling unspecified so upstream OpenImageIO defaults apply. Export settings do not change Save.
- **Export dialog:** `export.rs` owns the independent settings modal. Confirming settings opens the file chooser, then the GUI worker renders an immutable snapshot of the full-resolution input and simulation parameters through the same GUI `Runtime`. Loading an image, rotating input or editing controls after capture does not change that job. Export does not reuse reduced preview output or launch a `spektrafilm-f64` child. Its saving color space, transfer encoding and format options are independent of the simulation's Save settings.
- **Precision:** CPU Export uses the GUI build's native computation precision, and GPU Export uses WGPU f32 with faithful CPU stages where required. Output bit depth does not select computation precision. The separate CPU `spektrafilm-f64` CLI remains the f64 reference; CLI behavior is unchanged by this GUI workflow change.
- **Explicit output options:** JPEG Export exposes quality 1–100 and 4:4:4/4:2:0 chroma subsampling, and warns that JPEG is lossy even at quality 100. OIIO receives explicit quality through `CompressionQuality` and the requested chroma sampling. JPEG/PNG require 8-bit encoded samples. TIFF supports 8/16/32-bit and ZIP/none; EXR supports half/float, ZIP, and linear sRGB or ACES2065-1. These Export constraints are independent of upstream Save's permissive color/encoding behavior.
- **Cancellation and publication:** Cancel signals the worker. Running Pipeline computation or a native write may finish before the next cancellation boundary; the cancelled result is discarded before atomic output publication. Cancel does not kill a CLI process. Closing the GUI signals cancellation and joins the worker, so close may wait for an active computation. Viewer borders, watermark, display transforms and display ICC adjustments remain outside saved/exported pixels.
- **Single entry:** MAIN → Output contains one initially collapsed Export options area with Export/Cancel actions. Import RGB/Raw contain only import controls; bottom SAVE remains independent. The modal owns all Export settings.

- Both updated native acceptance Python scripts passed syntax compilation. Their complete interaction suites have not passed.
- The real native GUI under Xvfb loaded a 1024×768 image and produced a 640×480 Preview. Default WGPU selected `llvmpipe (LLVM 21.1.8, 256 bits)` (`Cpu`, Vulkan); this is software-adapter evidence, not hardware GPU evidence. With Vulkan drivers disabled for a separate process, automatic fallback rendered through `CPU (f32, rayon)`.
- The initial blocked acceptance was diagnosed on the subsequent run: Xvfb inherited the host session bus, and `rfd` synchronously waited for `org.freedesktop.portal.Desktop` activation for 120 seconds. The original log records `service_start_timeout=120000ms`. This blocked the UI's native chooser call; it was not evidence of a failed Scan pipeline. A fresh GUI completed full Scan immediately. Running an isolated session bus with GTK and desktop portals on the same Xvfb display restored Save.
- The native driver now checks the portal FileChooser interface and display before launching, distinguishes uppercase footer actions from `Scan for print`, and requires the requested Preview/Scan status. Clipboard helper output is detached from captured subprocess pipes. Use `xvfb-run -a -s '-screen 0 1600x1100x24' dbus-run-session -- <acceptance command>` with an installed GTK portal; do not reuse the host desktop bus for Xvfb. No host bus settings were modified.
- The real GUI completed Preview (640×480) → Scan (1024×768) → Save (TIFF16 ZIP). A fresh GUI also exported 1024×768 TIFF16 before any Scan. With the same parameters, seed 0, llvmpipe backend, sRGB encoding and TIFF16 options, both exports matched the saved Scan at every decoded channel: maximum error 0. Repeated Save retained the same pixels. Saving the current Preview left the render-completion count unchanged (5 before, 5 after).
- Native 100% and 400% Scan screenshots were compared with the full-resolution float32 export using nearest sampling and disabled display conversion. In the measured canvas region (x=50..979, y=150..799), maximum RGB8 difference was 1 at both zooms. This exercises full-source detail rather than magnification of the 640-pixel cache; it does not establish ICC/interpolator accuracy for every mode.

A later Export with +2 EV differed (maximum normalized channel difference 0.16160828), proving the edit was effective and isolated from the earlier job. Cancellation reached `Export cancelled` without publishing the target file.

Explicit GPU Export errors if no adapter exists; execution/device-loss errors are reported rather than silently rerendered on CPU. Hardware GPU confirmation is delegated to the user as requested; llvmpipe is not hardware evidence.
